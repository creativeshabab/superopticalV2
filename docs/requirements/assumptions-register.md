## Detailed Records

### ASSUMPTION-001: India GST Tax Calculation Model
- **Question:** How should the system handle intra-state vs inter-state sales and potential tax exemption categories?
- **Assumption:** The store's registered state and the customer's state code determine whether CGST + SGST (split equally) or IGST is charged. Products without a specific tax category default to a standard 12% optical goods rate.
- **Impact:** `@super-optical/tax` will implement intra/inter-state resolution and dynamic rate schedules.
- **Validation Required:** Review sample invoices from Bihar (Begusarai) and Uttar Pradesh (Ballia) stores to verify HSN codes and rates.
- **Owner:** Financial/Tax Architect
- **Status:** Active / Pending Validation

---

### ASSUMPTION-002: Offline Sync Conflict Resolution Workflow
- **Question:** If an offline device sells the last unit of a frame that was concurrently sold online or in another store, how should the server behave?
- **Assumption:** The server will accept the payment record to preserve the customer transaction, but flag the inventory deduction as a `CONCURRENT_STOCKOUT_CONFLICT`. The sale enters `PROCESSING_EXCEPTION` status for manager resolution (e.g., ordering from warehouse or supplier).
- **Impact:** Prevents financial loss while preventing silent inventory falsification.
- **Validation Required:** Confirm with store operations team if emergency negative inventory with immediate notification is permissible for retail sales.
- **Owner:** Offline & Inventory Architect
- **Status:** Active / Approved Direction

---

### ASSUMPTION-003: Store Device Authorization Policy
- **Question:** How are devices authenticated and tied to a physical retail counter?
- **Assumption:** Devices must pair via a one-time activation code generated by the store manager, producing a persistent cryptographic device certificate stored in secure client storage (Tauri secure store / Capacitor secure storage).
- **Impact:** Required for command idempotency and physical terminal tracking.
- **Validation Required:** Validate security requirements for Windows POS desktops vs staff Android tablets.
- **Owner:** Security Architect
- **Status:** Active / Pending Validation

---

### ASSUMPTION-004: Centralized vs Store Workshop Routing
- **Question:** Can a single retail store dispatch lens surfacing jobs to third-party labs while performing local frame fitting?
- **Assumption:** Lab jobs are split into lens procurement/surfacing jobs (external/central lab) and edging/fitting jobs (in-house or store workshop).
- **Impact:** Optical lab domain model includes `lens_orders` and `fitting_jobs` as distinct related entities.
- **Validation Required:** Review workshop workflow at Begusarai and Ballia stores.
- **Owner:** Product Engineer
- **Status:** Active / Approved Direction

---

### ASSUMPTION-005: Customer & Family Phone Number Scoping
- **Question:** Can multiple family members have distinct prescriptions and purchase histories under a single billing account?
- **Assumption:** A single Customer entity represents the primary account (with phone and billing address), linked to multiple `customer_family_members` who have independent clinical eye tests and prescriptions.
- **Impact:** Eliminates duplicate customer accounts while preserving individual medical histories.
- **Validation Required:** Confirm family tree depth (primary + dependents is sufficient).
- **Owner:** Clinical/CRM Architect
- **Status:** Active / Approved Direction

---

### ASSUMPTION-006: Cash Session Denomination Counting
- **Question:** Does the day close process mandate counting notes or only aggregate cash entry?
- **Assumption:** Both modes are supported: quick aggregate entry for fast closing and detailed denomination breakdown for strict cash reconciliation.
- **Impact:** Cash register domain entity accommodates an optional JSON denomination map alongside total count.
- **Validation Required:** Store manager sign-off during Phase 7.
- **Owner:** POS/Finance Architect
- **Status:** Active / Pending Validation

---

### ASSUMPTION-007: Legacy Data Migration Strategy
- **Question:** Will legacy invoices with unnormalized snapshots be imported as historical read-only revisions or full relational entities?
- **Assumption:** Migrated legacy invoices will be converted into historical `sales` rows with status `MIGRATED_LEGACY`, with best-effort line-item normalization and an attached unedited legacy JSON archive for audit safety.
- **Impact:** Avoids corrupting the new strict ledger constraints with incomplete historical data.
- **Validation Required:** Audit sample data dump from legacy Super Optical database.
- **Owner:** Database Architect
- **Status:** Active / Approved Direction
